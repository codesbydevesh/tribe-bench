## A. Root-cause report

### A.1 What ran

| | |
|---|---|
| Expected feature items | 1050 s x 2 Hz = **2100** |
| Encoded by the prepare pass | 17x120 + 60 = **2100** — the full stimulus, complete |
| Prepare bar | 4 h 31 m @ 7.72 s/item |
| A 19th encode *after* the bar finished | +15 m 33 s |
| Total GPU burned | **4.78 h** |
| Feature cache footprint had it been kept | **226 MiB** |

The encoding stage did its whole job correctly. Everything downstream of it failed.

### A.2 The two defects, both introduced by us

**Defect 1 — the features were never stored (cost: the entire run).**

`TribeModel.from_pretrained` assigns its `cache_folder` parameter straight into
`config["data.<mod>_feature.infra.folder"]` (`tribev2/demo_utils.py:206-208`),
*unconditionally*, clobbering the checkpoint's own `folder: CACHEDIR`
(`grids/defaults.py:86`). Its default is `None` and we never passed one. We separately
set `keep_in_ram: False` to bound RSS.

With folder `None` **and** keep_in_ram `False`, exca stores nothing:

```
exca/cachedict/core.py:127-128
    if self.folder is None and not keep_in_ram:
        raise ValueError("At least folder or keep_in_ram should be activated")

exca/map.py:290-291      except ValueError:  pass  # no caching
exca/map.py:504-507      except ValueError:        # no caching
                             return (out[k] for k, _ in uid_items)
```

The exception is *caught twice*. So `use_cache_dict=False` → `map.py:519 d = {}` → 4 h 31 m
of V-JEPA into a throwaway dict, returned as a generator, and **discarded** at
`neuralset/extractors/base.py:202`.

The released default is `keep_in_ram: True`. **Our optimisation is the proximate trigger:**
with `True` the prepare pass would have populated a RAM cache, the workers would have
inherited it copy-on-write, and there would have been no recompute and no crash.

**Defect 2 — the crash itself (a symptom, not a peer).**

Because nothing was cached, the dataloader legitimately found every item missing and
re-entered `_call_and_store` inside a forked worker. `neuralset/extractors/video.py:265`
does `model.model.to(self.image.device)`, where `device` is the literal string `"cuda"`
resolved in the parent (`extractors/base.py:516-517`) — hence
`Cannot re-initialize CUDA in forked subprocess`.

`num_workers = 20` is **`N_CPUS` from Meta's training cluster** (`grids/defaults.py:20,131`),
frozen into the released checkpoint config.

**Causal order matters:** with a warm cache the worker never reaches `_call_and_store`,
never builds the model, never touches CUDA. Fixing only `num_workers` would have converted
a loud crash into a **silent, correct-looking, ~9.5 h run**.

### A.3 The 19th encode

`neuralset/extractors/base.py:203-209` — after `_get_data(events)`, `prepare()` calls the
extractor once more on `events[0]` purely to learn the output shape. `_get_data` ignores
`duration` (`video.py:271-272`) and encodes the whole 60 s clip; the 1 ms crop is applied
afterwards. With a working cache it is a millisecond lookup.

## B. Independent audit findings

Five reviewers, disjoint remits, same source tree.

**A (execution path).** Traced all 24 transitions. Established that the prepare-pass and
dataloader **item uids are identical** — so a cache folder alone would have worked. Found
9 repeat-computation sites and 13 silent-fallback sites. Flagged the worst latent risk:
`main.py:200-212` silently deletes extractors with no matching events, and
`tribev2/model.py:188-192` zero-fills missing modalities — a run could complete and write a
report built entirely from `torch.zeros`.

**B (GPU/process safety).** Found that `num_workers` is a field of `Data`
(`main.py:112`), so the correct key is `data.num_workers`. Inventoried 17 CUDA-off-main-process
paths; `num_workers=0` closes exactly one. Four hardcoded `cluster="processpool"` defaults
sit dormant in the object graph; a WhisperX `uvx --device cuda` subprocess is reachable
before the dataloader if a stale sibling `.wav` exists.

**C (cache/reproducibility).** Item uid is
`f"{study_relative_path()}_{offset:.2f}_{duration:.2f}"` — the MASTER-PLAN's "path + offset +
duration, no content hash" verified exactly. Neither the stimulus bytes nor the V-JEPA
revision participate. No manifest, no expected count, no checksum: a partial cache is
indistinguishable from a complete one.

**D (adversarial).** Ranked 11 failure modes by damage x invisibility, and **refuted 11
hypotheses** (frame sampling is timestamp-based in 0.0.2; TR is 1.0 s; item uids are stable;
exca does raise on config drift; the cache is not committed as notebook output).

**E (test design).** 35 CPU-only tests, ~14 s total. Established that exca's five runtime
deps are all light — so the load-bearing tests can *fail* rather than skip.

### Corrections I made to my own reviewers

- C claimed `mode="read-only"` could not survive `folder=None` because the `ValueError` is
  swallowed first. **Refuted by execution** (§C.2): the swallow wraps only the lookup, so
  `missing` stays as every item and the read-only check still fires. Had I taken C's word I
  would have built a weaker firewall.
- I initially audited neuralset 0.2.3. Wrong file. Caught by comparing traceback line numbers.

## C. Proposed architecture

### C.1 Split the one expensive call into two stages

Today `predict()` prepares extractors and consumes them inside a single call, which is
precisely why "did the second stage recompute?" is unanswerable.

```
stage 1  --extract-features   may compute. Writes a verified artifact. Exits.
stage 2  --infer              verifies the artifact, then predicts. CANNOT compute.
```

### C.2 The firewall is a library feature we never switched on

`mode="read-only"` (`exca/map.py:311-313`) raises before any encoding. Measured on real
exca 0.5.20 with a fake encoder and a call counter:

```
A1  folder=None keep_in_ram=False mode=cached     -> 3 expensive calls, NO ERROR   <- THE INCIDENT
A2  folder=None keep_in_ram=False mode=read-only  -> RuntimeError                  <- fires even with no cache configured
B1  folder set, cold              mode=cached     -> 3 expensive calls
B2  folder set, WARM              mode=cached     -> 0 expensive calls
B3  folder set, WARM              mode=read-only  -> 0 expensive calls             <- the consume stage
C1  folder set, EMPTY             mode=read-only  -> RuntimeError                  <- injection case A
```

`expensive_calls == 0` is the observable "no-recompute proof". `mode` does not enter the
cache uid (`exca/base.py:191-194`), so the fix cannot invalidate what it protects.

Second lever, also off by default: `forbid_single_item_computation` (`map.py:150`) would
have caught the 19th encode in seconds.

### C.3 A durable artifact with a real identity

exca cannot express completeness, so we add it alongside:

```
<cache>/S2_FEATURES.json       manifest (tmp + os.replace)
<cache>/S2_FEATURES.COMPLETE   zero-byte marker, replaced LAST
```

carrying stimulus sha256, tribev2 revision + ckpt sha256, **V-JEPA revision +
processor-config sha256** (the gap exca has no way to close), neuralset/exca/tribev2
versions, design fingerprint, `n_items` **derived from the design** (never recorded from the
run — that would let a truncated run certify itself), and a per-item sha256.

`verify_manifest()` raises one of four typed errors and **never returns a boolean** — a
boolean invites `if not ok: recompute`:
`FeatureCacheMissing` · `Incomplete` · `Corrupt` · `Stale`.

This is load-bearing, not belt-and-braces: E measured that **exca returns corrupted features
silently** — overwriting 32 bytes of a `.data` file yielded `-1.18e+29` where `100.0` was
expected, with no error and no recompute.

## E. Test plan

35 CPU-only tests, ~14 s. `exca==0.5.20` becomes a dev dependency — its five runtime deps
(numpy, pyyaml, pydantic, submitit, orjson) are all light, so the load-bearing tests **fail
rather than skip** when it is absent.

| group | n | s | proves |
|---|---|---|---|
| E1 exca contract (subprocess) | 9 | 9.5 | stage 2 consumes without calling the extractor; the incident config recomputes; read-only fires |
| E2 artifact verifier (numpy only, **always run**) | 9 | 0.4 | injection cases A–D + G; corrupt/partial/stale each raise a typed error |
| E3 config + CUDA | 6 | 1.5 | effective `data.num_workers == 0`; no undotted keys; fork cannot init CUDA |
| E4 findings regressions | 10 | 2.8 | F2, F5, F8, ordering invariants |
| E0.1 anti-skip-rot guard | 1 | ~0 | fails the run if the exca tests silently skipped |

**The central test (E1.1)** runs a structural twin of `neuralset/extractors/video.py` as two
*separate subprocesses* — separate because a same-process test can pass state through
`keep_in_ram` while the disk cache is empty. Stage 1 `mode="cached"` → 6 calls; stage 2
`mode="read-only"` → **0 calls, 6 outputs, bit-identical**, tripwire absent.

**Cannot be covered CPU-only:** that torch's DataLoader really *forks* (needs the ~200 MB CPU
torch wheel — recommended, it closes the largest gap); whether `BaseExperiment` absorbs the
stray key (one Kaggle command); real V-JEPA values; Kaggle filesystem semantics.

## G. GPU cost estimate

| | |
|---|---|
| Feature extraction (stage 1) | ~4.75 h, **once** |
| Brain-model forward (stage 2, warm cache) | minutes |
| Atlas + floors | ~10 min (moved before the GPU pass) |
| **Total, healthy** | **~5.0-5.5 h** |

The notebook's stated 3.4 h budget is ~40% low; `s2_design.py:312`'s
`compute_s_per_stimulus_s = 11.5` is the stale input.

**Why the 4h45m cannot silently repeat.** Stage 2 runs with `mode="read-only"`. A cache miss
— from any cause: absent, partial, corrupt, stale, moved, re-rendered stimulus, changed
revision — raises `RuntimeError` *before any frame is encoded*. There is no code path from
"cache missing" to "encode again" in stage 2, because exca refuses at `map.py:311-313`.

**Cost gate.** V-JEPA encoding can occur **exactly once** per S2 invocation (only stage 1 may
compute; stage 2 physically cannot). Across a crash/restart: **at most once** per
`(stimulus sha256, model revision, V-JEPA revision, preprocessing config)` identity, provided
the cache outlives the session — which today it does **not** (F7, `/kaggle/temp`). Until F7 is
resolved, honest answer: **once per session, not once per identity.**
